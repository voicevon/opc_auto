# 代码重构标准化工作协议 (Refactor Protocol)

本协议定义了在本项目（OPC Auto）中开展代码重构的标准作业流程。本协议吸收了业界经典重构理论（马丁·福勒《重构》、肯特·贝克测试驱动与 Mikado 重构推导法），并与根目录 [AGENTS.md](file:///d:/Software/opc_auto/AGENTS.md) 核心开发准则强绑定。

---

## 一、 核心重构基石与原则

1. **“两顶帽子”原则（严禁功能混杂）**：
   - 开发者或 AI 在任一时刻只能戴一顶帽子：要么**添加新功能**，要么**重构代码**。
   - 重构过程中**严禁私自变更既有外部业务契约与对外行为**。修复偶发 Bug 或新增特性必须拆分为独立任务。
2. **“步步常绿”与微重构（Small Incremental Steps）**：
   - 严禁一次性大范围重写（Big Bang Rewrite）。
   - 将大型重构拆解为可独立验证的原子微步骤（每次改动单一职责），每个微步骤后必须验证测试全绿。
3. **零历史包袱，彻底物理删除（No Backward Compatibility）**：
   - 重构不保留任何向后兼容层、历史废弃别名、回退 fallback 分支或胶水适配器。
   - 所有调用点一次性全量迁移，旧代码与废弃接口直接物理删除。
4. **单一真理源 (SSOT) 与拒绝重复 (DRY)**：
   - 业务参数、配置、预设项与规则枚举必须收敛至唯一权威源，坚决杜绝前后端双轨硬编码或跨模块散落。

## 二、 代码坏味道识别清单 (Code Smells Audit)

在启动重构前，必须使用工具全面扫描并识别目标代码的具体坏味道：

| 坏味道类型 | 具体特征与判定标准 | 针对性重构技术 (Refactoring Technique) |
| :--- | :--- | :--- |
| **神仙类 / 臃肿模块** (God Class / Long File) | 单文件超过 400 行、承载数据读取、业务处理、网络请求、渲染多重职责 | **提炼模块/服务 (Extract Module/Service)**：按业务单一职责拆分 |
| **单一真理源违规** (SSOT Violation) | 同一配置或预设在 Python、HTML、JS 中各自散落写死，无法一处修改全局生效 | **收敛至统一真理源**：抽离至统一配置文件，并通过后端 API 统一分发 |
| **重复逻辑与魔数** (Duplicated Code / DRY Violation) | 相似的异常处理、清洗算法、DOM 操作在多处直接复制粘贴；散落无名硬编码 | **提炼公共工具函数 (Extract Function)**、引入权威常量定义 |
| **散弹式修改** (Shotgun Surgery) | 每次修改一个细微业务逻辑，需要同时改动 3 个以上不同模块的代码 | **搬移函数/内聚职责 (Move Function / Consolidate)**：将强相关逻辑合并归仓 |
| **依恋情结** (Feature Envy) | 某个类或函数频繁跨界调用另一个类/模块的数据与私有属性 | **转移职责 (Move Method)**：将逻辑移至数据实际持有的模块内 |
| **过度设计与冗余包装** (Speculative Generality) | 只有一个实现却设计了复杂的抽象工厂、多层封装 Wrapper 或未使用的参数 | **内联与简化 (Inline Function / YAGNI 瘦身)**：依据 Ponytail 协议平铺实现 |

## 三、 重构四步标准化流程

### 第 1 步：诊断排查与安全网构建（先读后动）
1. **全局影响面扫描**：
   - 通读目标代码，使用 `grep_search` 全局检索目标函数、类、配置键名的所有调用方及测试用例。
2. **测试防护网核验 (Safety Net)**：
   - 检查目标模块是否有完备的自动化单测支撑；
   - 若缺失单测，**重构前必须先补充基准特征测试（Characterization Tests）**，固化重构前的正确行为基准。
3. **出具重构方案清单**：
   - 列出明确的改动方案、涉及模块及潜在风险，等待用户确认后再开始动手。

### 第 2 步：命名决策与交互确认 (严格准则)
1. **严禁擅自修改命名**：
   - 拆分产生的新文件名、类名、函数名或关键公共变量名，绝对禁止由 AI 直接私自决定或随意重命名。
2. **提供 3~5 个候选方案**：
   - 必须准备 3 至 5 个高品质候选名称，附带命名理由与语义侧重点。
3. **交互式选择题确认**：
   - 必须调用 `ask_question` 工具以交互式选择题形式呈现给用户点选确认，确认后方可落地。

### 第 3 步：原子微步骤实施 (Micro-Refactoring)
1. **自底向上推进**：
   - 优先抽取纯逻辑、无副作用的底层工具函数与数据模型；
   - 逐步重构中层服务，最后改写上层顶层调度与控制器。
2. **迁移与清理同步进行**：
   - 新实现就绪后，直接在所有调用点全量切换为新接口；
   - **立即物理删除废弃旧实现**，不留任何过渡期代码。
3. **临时实验严格隔离**：
   - 重构调试脚本、临时比对数据必须且只能保存在 `temp/` 目录中，严禁污染业务目录。

### 第 4 步：验证、回归与交付
1. **分级测试验证**：
   - 先执行目标模块的专项单测；
   - 再执行全量测试套件（运行单元测试与 API 冒烟测试），确保 100% 绿色通过。
2. **工作区状态自检**：
   - 执行 `git status -s`，仔细核对改动清单，确保无无关文件、运行时临时文件混入。
3. **严禁自动提交**：
   - 绝对禁止执行 `git commit` 或 `git push`；交付以工作区就绪并出具清晰汇报为准。

## 四、 复杂依赖解耦：Mikado 重构推导法

当面临大型、深层耦合模块的复杂重构时，必须采用 **Mikado 探索法**：

```text
[设定最终重构目标]
       │
       ▼ (尝试直接改动)
   [遇到阻碍/编译报错/测试挂掉]
       │
       ├─► 1. 立即 git checkout 回滚当前改动（保持主干干净）
       ├─► 2. 在记录中记录该前置先决条件（Prerequisite）
       ├─► 3. 转去优先实现该先决条件（叶子节点重构）
       └─► 4. 先决条件就绪并全绿后，再次尝试目标
```
通过递归消除前置依赖，保证重构过程中系统的代码库**时刻处于可运行、随时可测试的健康状态**。

## 五、 重构完成汇报格式规范

重构完成后，以清晰的 Markdown 结构向用户汇报：

```markdown
### 🛠️ 重构执行概述
- **重构目标**: [说明重构的目标模块与核心诉求]
- **坏味道消除**: [列出消除了哪些坏味道，如抽离了哪些重复逻辑、收敛了哪些散落配置]

---

### 📊 结构变迁对照表
| 重构前结构 / 问题做法 | 重构后结构 / 新实现 | 收益与架构改善 |
| :--- | :--- | :--- |
| `旧模块 A 混合了网络与解析` | `拆解为 NetworkClient 与 DataParser` | 职责单一，便于独立单元测试 |
| `前端与后端各自写死配置常量` | `收敛至 scheduler_config.json，API 驱动` | 达成 SSOT 单一真理源，零双轨维护 |

---

### 🧪 验证结果
- **针对性单测**: ✅ 100% 通过 (N 个测试用例)
- **系统回归测试**: ✅ 100% 通过
- **工作区状态**: 仅改动目标文件，零临时文件污染，未执行 Git Commit。
```
